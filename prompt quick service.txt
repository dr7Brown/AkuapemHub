# AkuapemConnect — Quick Services Module

Build a new **Quick Services** module inside the existing AkuapemConnect web application.

## CRITICAL DEVELOPMENT RULE

**DO NOT build the module from scratch.**

Before writing any code:

1. Inspect the existing AkuapemConnect codebase thoroughly.
2. Identify existing reusable components, database tables, models, controllers, services, routes, authentication, roles, permissions, admin dashboards, manager functionality, payment processing, Paystack integration, notifications, email/SMS functionality, file uploads, UI components, cards, forms, modals, tables, status badges and audit/logging systems.
3. Reuse existing components wherever they already provide the required functionality.
4. Extend existing components when practical instead of creating duplicates.
5. Only create new components when the existing system genuinely does not provide the required functionality.
6. Do not create a second authentication system, payment system, notification system, user system, manager system or admin system.
7. Do not introduce another UI framework or unnecessary dependency.
8. Do not modify unrelated AkuapemConnect modules unless absolutely necessary.

The goal is to make Quick Services feel like a **native part of AkuapemConnect**, not a separate application.

---

# 1. QUICK SERVICES PURPOSE

Create a customer-facing module called:

**Quick Services**

It will allow AkuapemConnect users to conveniently purchase/request commonly needed digital services.

The initial services are:

1. **Buy Data**
2. **BECE/WASSCE Result Services**

More services will be added later.

The architecture must therefore be **extensible and database-driven**.

Future services may include:

* Airtime
* ECG Prepaid
* TV subscriptions
* School application forms
* Admission forms
* Other digital services

Do not hard-code the system around only the initial services.

* Telecel

### Bundle

Examples:

* 500MB
* 1GB
* 2GB

* 10GB
* 20GB

Admin should be able to:

* Add bundle
* Edit bundle
* Change price
* Activate/deactivate bundle
* Change display order

### Recipient Number

Validate the phone number appropriately.

# 6. BUY DATA PAYMENT

After the customer selects the bundle:

Show an order summary:

* Network
* Bundle
* Recipient number
* Price
* Total

**Pay Now**

# 7. QUICK SERVICE TRANSACTION

Create a reusable Quick Services transaction structure, but reuse the existing transaction/payment table if it can safely support the functionality.

Do not create duplicate transaction records unnecessarily.

The transaction should contain or reference:

* Unique transaction reference
* User
* Service
* Amount
* Payment status
* Processing status
* Assigned manager
* Customer information
* Service-specific information
* Notes
* Created date
* Updated date
* Completed date

Keep **payment status** separate from **processing status**.

### Payment status

* Pending
* Paid
* Failed
* Refunded

### Processing status

* Awaiting Assignment
* Assigned
* Processing
* Completed
* Failed
* Cancelled

# 8. SERVICE-SPECIFIC DATA

The transaction architecture must allow different services to store different information.

For example, Buy Data needs:

* Network
* Bundle
* Recipient number

BECE/WASSCE needs:

* Examination type
* Examination year
* Index number
* Candidate information
* WhatsApp number
* Service option

Use the existing database conventions where possible.

If the current application uses structured tables for service-specific information, follow that pattern.

If no suitable pattern exists, use a clean flexible approach without overengineering the system.

---

# 9. MANAGER ASSIGNMENT

Quick Services transactions must be processed by authorized managers.

Reuse the existing manager/user/role structure.

Create a relationship between:

**Manager ↔ Quick Service**

Example:

Manager A:

* Buy Data
* BECE Checker

Manager B:

* WASSCE Checker
* Result Checking

Admin should be able to assign services to managers.

A manager must only see transactions for services they are authorized to process.

Do not expose unrelated customer transactions.

* Customer
* Phone
* Service
* Amount
* Payment status
* Processing status
* Service-specific information

* Notes

**Mark Completed**

* Upload the result PDF

# 15. RESULT PDF SECURITY

Result PDFs may contain sensitive student information.

Do not place them in a publicly accessible uploads directory.

Reuse the existing secure file storage system if available.

Only authorized:

* Customer
* Assigned Manager
* Authorized Admin

should be able to access the document.

Do not expose predictable public file paths.


# 25. SECURITY

Follow existing AkuapemConnect security conventions.

Ensure:

* Authentication required
* Proper authorization
* CSRF protection where applicable
* Server-side validation
* Payment verification
* Secure file handling
* No sensitive information in URLs
* No unauthorized manager access
* No customer access to another user's transaction
* No direct manipulation of transaction status
* Proper database queries/prepared statements
* Proper escaping/output handling

# 26. MOBILE-FIRST DESIGN

Quick Services will primarily be used from phones.

Customer screens should therefore be:

* Simple
* Fast
* Mobile-first
* Touch-friendly
* Minimal form fields
* Clear status indicators
* Easy Paystack checkout

Reuse AkuapemConnect's existing responsive components.

Do not redesign the entire application.

---

# 27. PERFORMANCE

Keep the module lightweight.

Do not introduce unnecessary libraries.

Reuse existing:

* CSS
* JavaScript
* components
* database helpers
* APIs
* notification infrastructure

Avoid unnecessary database queries.

Use pagination for transaction lists.

Do not load thousands of transactions into the browser at once.

# FINAL DEVELOPMENT INSTRUCTION

**The most important requirement is reuse.**

Do not assume that every feature needs a new implementation.

Before creating any:

* table
* model
* controller
* route
* service
* component
* notification system
* payment function
* dashboard
* manager system
* file upload system

first search the existing AkuapemConnect codebase for equivalent functionality.

If an existing component can perform 70–80% of the required task, extend/reuse it instead of creating another parallel implementation.

Keep Quick Services modular, lightweight, secure and easy to extend.

**Do not break existing AkuapemConnect functionality.**

At the end of implementation, provide a summary of:

1. Existing components reused
2. Existing components modified
3. New files created
4. Database changes
5. New routes
6. New permissions
7. New environment/configuration requirements
8. Testing performed
9. Any remaining TODOs
